Phase 3: The Dynamic Taint Analysis Engine (C++)
With a working emulator, you turn it into a security sandbox.

3.1 Shadow Memory:

Create a parallel 64KB array (std::vector<uint8_t> shadow_memory).

0 means untrusted (clean), 1 means tainted.

3.2 Taint Sources (The Attack Vector):

Flag all data coming from the Joypad register (0xFF00) or specific mutated ROM headers as tainted (value = 1).

3.3 Taint Propagation:

Modify your CPU's Execute loop. If a tainted register A is added to register B, register B becomes tainted. If tainted data is written to memory, that shadow memory address becomes tainted.

3.4 Taint Sinks & Traps:

Hook sensitive instructions (like JP, CALL, RET). If the CPU attempts to jump to a tainted address, halt the system.

Milestone 3: Write a custom homebrew ROM that overflows a buffer via joypad inputs. The C++ engine should successfully trap it and call exit(139).

Phase 4: Fuzzing & Logging (Simultaneous Python + JS)
As requested, we build the external tooling simultaneously. While Python bombards the C++ engine with data, JS serves the crash reports.

4.1 The Python Mutator (fuzzer/mutations/):

Write Python scripts to take a valid Game Boy ROM or input stream, apply bit-flips, byte-swapping, or magic-number injections, and output mutated_test.gb.

4.2 Headless Fuzzing Loop (fuzzer/fuzzer_main.py):

Orchestrate the loop: Python spawns AegisCore.exe --headless mutated_test.gb.

Monitor the exit code. If C++ hits a Taint Trap (e.g., exit code 139), Python saves the mutated ROM and triggers the log generation.

4.3 Diagnostic Log Export (C++):

Upon crashing, C++ uses <fstream> to write a trace.json containing the last 100 executed instructions, register states, and the shadow memory map.

4.4 Threat Reporting Dashboard (reporter/server.js):

The Node.js server watches the build/logs/ directory.

When a new trace.json appears, the JS backend parses it and updates the public/index.html frontend.
